## 3. 업그레이드 A — 질문 해석을 일관되게 처리

가장 먼저 요청의 업무·신청 유형·원하는 항목을 검색 이전부터 일관되게 해석해줘.

확인된 재현 사례:

- `성인 여권 재발급 준비물`에는 기존 여권 지참을 답하지만 `성인 여권 재 발급 준비물 알려줘`에는 그 항목과 사유별 추가서류 주의가 빠진다.
- `어른 여권 다시 발급받으려면 뭘 가져가야 해?`에는 신규/재발급인지 불필요하게 다시 묻는다.
- `희망 도서 월별 신청 한도 알려줘`에는 권수 대신 신청 절차를 답한다.
- `대형 폐기물 어떻게 버려요?`에는 이미 명확한 배출 방법을 다시 선택하라고 묻는다.
- `주민등룍증 발급 절차 알려줘`는 오타 때문에 근거 부족으로 끝난다.

수정 방향:

1. `query_subject.py`, `conversation.py`, `response_helpers.py`, `answer_goal.py`, `passport_documents.py`의 해석 순서를 추적해줘. 현재는 RAG 검색 직전에만 정규화되는 반면 확인 질문·여권 준비물 분기는 그보다 먼저 실행되는 불일치가 있다.
2. 공통 질의 해석을 적절한 진입점에서 적용하고, 업무 식별·신청 유형·요청 항목·후속 문맥이 같은 의미를 사용하게 해줘. 원래 사용자 입력은 개인정보 검사와 대화 기록에 보존해줘.
3. 띄어쓰기, 활용형, 의미가 명확한 약칭·오타를 처리하되 숫자·연령·지역·신규/재발급·부정 표현을 임의로 바꾸지 마. 애매한 교정은 한 가지 확인 질문으로 처리해줘. 무제한 유사 문자열 치환은 금지한다.
4. `신규가 아니라 재발급`, `발급 말고 분실 신고`, `부모가 신청하는 미성년자`, `성인 대신 대리 신청`을 서로 구분해줘. 필요 조건이 빠진 경우의 확인 질문은 유지해줘.
5. 요청 항목은 동사 `신청`만으로 결정하지 말고 권수·횟수·금액·기간·서류·위치·조건 등 실제 요구를 구분해줘. `한도`를 전부 금액 또는 일정으로 취급하지 마.
6. 질문 하나에 답변을 박아 넣는 예외를 늘리지 말고, 동의 표현은 해석 단계에서, 값과 조건은 검증된 공식 원문에서 가져오게 해줘.

완료 기준: 위 오류의 실제 API 재현이 해결되고, 의미가 다른 반례와 기존 안전·후속 대화 검사도 유지되어야 한다. 전용 회귀 테스트와 실제 API 결과를 남긴 뒤 첫 업그레이드를 커밋·푸시해줘.

## 4. 업그레이드 B — 질문과 답변 근거의 실제 업무·조건 일치

우선 고칠 위험 사례:

- `보건소 주소는?`에 보건소 건물 주소 대신 폐렴구균 예방접종 장소를 답한다. 이전 자전거 대화에서 새 주제로 넘어온 실제 시나리오에서 재현됐으며, 문맥 구성 자체는 새 질문을 유지했다.
- `둘째 아이만 있어도 광안대교 통행료가 무료인가요?`에 통행료 감면 조건 대신 다른 출산지원 안내의 일반적인 둘째 출산가정 대상을 답한다.
- `희망도서는 어디서 신청하고 어떤 책은 제외돼요?`에 제외 기준이 빠진다.

수정 방향:

1. 검색 후보의 관련성과 최종 답변 가능 여부를 분리해줘. 벡터 유사도나 BM25 점수는 사실성·정답 확률이 아니다.
2. 문서 제목·본문의 실제 항목·표의 행/열·하위 사업·적용 대상·예외를 함께 확인해줘. 페이지가 같은 사업군이라는 이유만으로 다른 항목의 조건을 가져오면 안 된다.
3. 기관 자체의 위치·운영시간과 개별 검진·접종·교육 사업의 장소·시간을 구분해줘. 올바른 기관 소개/오시는 길 자료가 검색에서 탈락하는 원인도 함께 고쳐줘.
4. 복합 질문은 항목별 근거 충족 여부를 검사해줘. 일부만 입증되면 확인된 내용을 짧게 안내하고 미확인 항목을 명시해줘. 중요한 자격·제외·추가서류가 누락된 답을 완전한 답변으로 표시하지 마.
5. 같은 검증 기준을 구조화 답변, LLM의 근거 선택, 원문 추출 fallback 등 모든 출력 경로에 적용해줘. 한 경로의 검증 실패가 약한 다른 경로로 우회되지 않게 해줘.
6. 올바른 자료가 검색되지 않는 문제, 자료는 있지만 필요한 조건이 없는 문제, 공식 자료 자체가 오래된 문제를 구분해줘. 공식 페이지를 실제 확인한 뒤 자료 보강이 필요하면 수집·원문 보존·색인을 갱신해줘. 외부 지식을 모델 기억으로 채워 넣지 마.

완료 기준: 잘못된 사업 안내 사례가 올바른 조건 안내 또는 명확한 근거 부족 안내로 바뀌고, 출처가 실제 답변 항목을 뒷받침해야 한다. 안전하게 거절했다고 자료가 있는데도 답하지 못하는 문제까지 해결된 것으로 계산하지 마. 검증 후 두 번째 업그레이드를 커밋·푸시해줘.

## 5. 업그레이드 C — 실제 자료 갱신과 중단 후 복구

10/15 검사 당시 직원 안내 자료가 10/7 확인 상태라 7일 유효기간을 넘었다. Worker 로그에는 예약 갱신들이 16~18시간 지연되어 실행되지 않은 기록이 있다. `worker.py`는 cron에 `misfire_grace_time=3600`을 사용하고 시작 직후 전체 갱신을 보장하지 않는다.

1. 절전·오프라인·프로세스 재시작 등 긴 공백 이후 누락된 갱신을 복구하도록 설계해줘. 마지막 **성공** 시각을 기준으로 시작 시 또는 주기적으로 기한이 지난 작업을 판단해줘.
2. 중복 실행 방지, 실패 시 재시도 간격, 타임아웃, 마지막 정상 자료 보존, 원자적 저장을 포함해줘. 일부 페이지 실패를 전체 갱신 성공으로 숨기지 마.
3. 직원 업무·연락처와 공식 페이지를 실제 재확인해줘. 확인일만 새 날짜로 바꾸거나 7일 기준을 늘려 오래된 연락처를 노출시키면 안 된다.
4. 채팅 요청마다 동기 크롤링을 실행하지 마. 갱신 실패는 추적 가능하게 기록하고 응답 경로는 안전하게 유지해줘.
5. 기존 부서명 추출 테스트를 고정된 공식 데이터 fixture/시간으로 분리해줘. 만료·미확인·미래 시각의 자료를 거부하는 별도 테스트는 유지하거나 추가해줘.

완료 기준: 정상 갱신, 오래된 자료, 갱신 실패, 재시작/긴 지연 후 복구가 검증되고 실제 갱신 결과가 기록되어야 한다. 세 번째 업그레이드를 커밋·푸시해줘.

## 6. 업그레이드 D — 정확성 검증을 유지한 응답시간 개선

현재 일부 답변은 38~43초가 걸린다. 단순 확인 질문은 수십 밀리초일 수 있으므로 모든 답변을 같은 속도로 맞추려 하지 말고, 사실 안내 경로 내부의 지연 원인을 줄여줘.

1. 질문 해석, DB/원문 조회, BM25, 벡터 검색, 재정렬, 원문 파싱, 근거 선택, LLM 처리 시간을 분리 계측해줘. 먼저 병목을 측정하고 실제로 큰 부분부터 고쳐줘.
2. 후보: 동일 요청의 중복 벡터 조회, 대량 원문 반복 조회·파싱, 구조화 가능한 항목이 불필요하게 느린 경로로 가는 현상, 모델 초기 로딩. 이들은 조사 대상이지 확인 없이 적용할 처방이 아니다.
3. 캐시를 적용한다면 원문/자료 버전과 모델·설정 변경을 반영하고 만료·변경 자료를 다시 검증해줘. 캐시된 옛 답변을 최신 답변처럼 재사용하지 마.
4. 타임아웃·실패 시에도 검증된 근거로 답하거나 미확인을 안내해줘. 근거 검사를 생략하거나 출력을 잘라 조건을 잃지 마.
5. 같은 PC·모델·자료·동시 부하 조건에서 개선 전후를 비교해줘. 초기 로딩과 준비된 상태, 실제 답변과 확인 질문, 캐시 적중과 미적중을 구분하고 중앙값/p95/최장 시간을 기록해줘. 질문 하나를 반복해 얻은 캐시 속도를 일반 응답속도로 발표하지 마.

완료 기준: 주요 느린 경로의 지연 원인과 개선 결과가 수치로 확인되고 답변·조건·출처 검증이 유지되어야 한다. 네 번째 업그레이드를 커밋·푸시해줘.

## 7. 최종 검증 및 계획서 이행 점검

- 기존 전체 회귀 테스트와 실제 API 검사를 수행해줘. 단위 테스트 통과율을 실제 정답률이라고 쓰지 마.
- 계획서의 최소 100개 행정 질문 목표에 맞춰 평가셋을 점검·보강하되, 의미가 같은 변형과 다중턴을 별도 집계해줘. 기존 제공 질문, 개발용 질문, 독립 최종 검증 질문을 구분해줘.
- 최종 검증은 튜닝에 쓰지 않은 표현 10개와 추가 독립 질문을 포함해줘. 독립 검증에서 오류를 고쳤다면 그 문항은 개발셋으로 옮기고 새 최종 검증 문항으로 교체해줘.
- 일반 질문, 드문 질문, 띄어쓰기·말투·오타, 신규/재발급·연령·대리인·부정 표현, 복합 질문, 짧은 후속 질문, 주제 전환, 없는 사업, 오래된/충돌하는 정보, 개인정보, 긴급 질문을 포함해줘.
- 질문마다 `충분하고 정확한 답변 / 필요한 확인 질문 / 타당한 부분 답변 / 타당한 근거 부족 안내 / 불필요한 거절 / 잘못된 업무·사실·조건 / 실행 오류`를 구분하고 근거 URL·확인일·채점 이유를 남겨줘.
- 공식 원문에 있는 문장을 복사했더라도 질문과 다른 업무라면 오답이다. 출처 링크만 달렸다고 출처 적합으로 판정하지 마.
- 숫자·연령·날짜·금액·부서·전화번호·예외 조건을 원문과 대조해줘. 크롤링 확인일과 본문 정책 적용일을 구분해줘.
- `document/project_context.md`의 항목별로 구현 확인, 실제 동작 확인, 미완료를 나누어 보고해줘. 특히 첨부 PDF/HWP 처리 범위, 최신성, 문맥, 출처, 개인정보, 평가 목표를 확인해줘. 10명 이상 사용자 평가는 실제 수행 증거가 없으면 미완료로 남겨줘.
- 확인된 한계와 평가 범위를 명시해줘. 일부 테스트 성공을 전체 질문의 100% 정확도·환각 0% 보장으로 표현하지 마.

## 8. 커밋과 최종 산출물

각 업그레이드는 `원인 확인 → 공통 로직 수정 → 관련 회귀 검사 → 실제 API 확인 → 변경 내용과 남은 한계 기록 → 명시적 파일 선택으로 커밋 → 해당 브랜치에 push` 순서로 진행해줘. 마지막에 전부 묶어 한 번만 커밋하지 마. 단계가 너무 크면 검증 가능한 단위로 더 나눠도 된다.

최종적으로 다음을 제공해줘.

1. 수정 전 문제와 근본 원인, 수정 후 실제 답변 비교.
2. 평가 질문 수·턴 수·구분·실행 시각·기준 커밋·모델·자료 상태·채점 기준.
3. 정확성, 중요한 조건 누락, 출처 적합성, 불필요한 거절, 표현 변형 일관성, 응답시간의 비교.
4. 계획서 이행 상태와 남은 문제, 자료 부족과 코드 문제의 구분.
5. 업그레이드별 커밋 해시와 GitHub 브랜치 링크, 실제 원격 푸시 확인 결과.
6. `document/project_context.md` 갱신 및 재현 가능한 평가 보고서.

작업 도중 문제가 예상과 다르면 근거를 바탕으로 순서를 조정해도 된다. 다만 **잘못된 사실·업무·조건 안내 방지 → 같은 의미의 질문 처리 → 자료 최신성 → 속도**라는 우선순위를 유지해줘.
