받은 피드백

지적 사항

"실제 주민들이 사용하게 될 경우를 대비해, 최소 100명 이상이 동시 접속했을 때도 속도 저하 없이 비슷한 성능을 유지할 수 있는지 부하 테스트가 필요하다."

→ 타당한 지적입니다. 다만 답변의 핵심은 "무엇이 동시 처리 성능을 결정하는가"를 정확히 짚는 데 있습니다.

핵심 논리

동시 처리 성능을 결정하는 것

동시 접속 처리 능력은 앱 구조가 아니라 LLM 백엔드의 추론 처리량에 의해 결정됩니다.
  • 웹 서버 계층 (FastAPI 비동기 + 워커 스레드풀)은 다수의 동시 접속 자체를 이미 비차단으로 처리합니다.
  • 실제 응답 속도를 좌우하는 병목은 LLM 모델의 추론 속도 한 곳입니다.
  • 그리고 이 LLM 백엔드는 우리 시스템에서 교체 가능하게(swappable) 설계되어 있습니다.
데모 vs 운영

Groq(발표 데모)와 Ollama(실제 운영)는 다릅니다

발표 데모 Groq API

  • 무료 티어 정책상 요청 간 최소 간격 제한이 걸려 있음
  • 즉 데모의 동시 처리 수치는 무료 API 정책 때문이지 시스템의 한계가 아님
  • 빠른 시연·발표에는 충분

실제 운영 Ollama 자체 호스팅

  • 외부 API 제한 없음 · 비용·쿼터 제약 해소
  • 주민 데이터가 외부로 안 나감 → PII 보안 유리
  • 동시 처리량은 운영 서버 GPU 사양에 따라 확장

→ 따라서 의미 있는 부하 테스트는 운영 환경(Ollama + 실제 서버) 기준으로 수행해야 합니다.

동시성 병목이 "외부 API 정책" → "우리가 통제하는 하드웨어"로 이동합니다.

대응 계획

책임 있는 검증 로드맵

STEP 1

병목 제거

데모용 요청 간격 제한 등 인위적 직렬화 요소를 운영 구성에서 제거

STEP 2

처리량 확보

운영 모델·GPU 사양에 맞춰 병렬 처리 수와 요청 큐를 튜닝

STEP 3

부하 테스트

100명+ 동시 접속 시나리오로 응답시간·처리량·실패율 측정

부하 테스트 하니스(스크립트)는 미리 준비해두고, 배포 서버 사양이 확정되는 시점에 운영 환경 기준으로 측정합니다.

예상 질문 대비

Q&A 대비

Q. 그럼 지금 데모로는 100명 못 받는 거 아니냐?
A. 데모 환경(무료 Groq)에는 외부 API 정책상 제한이 있는 게 맞습니다. 하지만 그것은 운영 구성이 아니며, 실제 배포(Ollama)에서는 해당 제한이 없습니다.
Q. Ollama로 하면 100명 정말 되냐?
A. 동시 처리량은 GPU 사양에 비례합니다. 모델 크기·서버 사양에 맞춰 병렬 처리 수를 튜닝하고, 실제 주민 사용 패턴(전원이 같은 순간 전송하는 건 아님)을 반영한 부하 테스트로 검증하겠습니다.
⚠️ 주의: "지금도 100명 거뜬합니다"라고 단언하면 역공당합니다(데모 환경 제한 때문에 실제로는 못 버팀). "백엔드 교체로 해결되는 구조 + 운영 환경에서 검증 예정"으로 프레이밍하는 것이 정직하면서도 안전합니다.
한 줄 요약
"동시 접속 성능은 LLM 백엔드 처리량이 결정하며, 우리 시스템은 그 백엔드를 교체 가능하게 설계했습니다. 데모는 Groq, 운영은 Ollama이며, 부하 테스트는 운영 환경 기준으로 검증합니다."

정직함 + 구조적 해결 가능성 + 검증 계획 — 세 가지를 함께 전달하는 것이 핵심.
