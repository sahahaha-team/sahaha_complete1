# 신뢰도 게이트 + 파일 인제스트 + 첨부파일 노출 + 검색 랭킹 개선 (2026-06-21)

> 다음 4개 기능을 한 차례에 추가/개선한 작업.
>
> 1. **답변 신뢰도 게이트** — 근거 부족/도메인 밖 질문 시 안전 안내 멘트 출력 (환각 방지 + API 절약)

> 3. **첨부파일 노출** — 게시물의 PDF/HWP 다운로드 링크를 답변 출처 카드에 표시

>

## 2. 답변 신뢰도 게이트

근거가 부족한 질문에 LLM이 그럴듯한 환각을 만드는 것을 줄이기 위해, 검색 결과의
신뢰도가 낮으면 LLM을 호출하지 않고 안전 안내 멘트를 출력한다.

### 설계 포인트
- **유사도만으로는 판정 불가**: 임베딩 모델(MiniLM-L12-v2)은 무관한 질문에도 코사인
  유사도가 0.7~0.8로 압축돼, 절대 임계값만으로는 도메인 밖 질문을 못 거른다.
- **하이브리드 점수도 부적합**: 후보 풀 내 min-max 정규화라 최상위가 항상 ~1.0 →
  원본 벡터 유사도(`vector_similarity`)를 별도로 보존해 사용.
- **키워드 겹침 + 한국어 조사 제거**: 질문 키워드(순수 숫자·불용어 제외, "위치와"→"위치"
  조사 제거)가 상위 문서에 실제로 등장하는지 확인.
- **보수적 판정(OR)**: `유사도 충분 OR 키워드 겹침` 중 하나라도 만족하면 통과.
  (둘 다 요구하면 동의어·조사 차이로 정상 질문이 차단되는 false negative 발생 →
  실제로 "사하구청 위치와 연락처" 질문이 잘못 차단되는 버그가 있어 OR로 완화)

### 변경 파일
- [chatbot/retriever.py](../chatbot/retriever.py) — `assess_confidence()`, `_content_keywords()`, `_strip_josa()`
- [chatbot/conversation.py](../chatbot/conversation.py) — `chat()`에 게이트 분기 추가
- [config.py](../config.py) — `CONFIDENCE_MIN_SIMILARITY`(기본 0.45), `LOW_CONFIDENCE_MESSAGE`

> 참고: 발표자료의 "정확도 85% 이상" 문구는 LLM 자가 신뢰도 점수가 아니라 **검색 유사도
> 임계값**으로 매핑했다. LLM 자가 점수는 보정(calibration)이 안 돼 신뢰하기 어렵기 때문.

## 3. 파일 단위 인제스트 (PDF / HWPX / HWP)

웹 크롤링과 동일하게 `PageData` 호환 객체를 만들어 반환하므로, 이후 정제·태깅·임베딩·검색
파이프라인은 수정 없이 그대로 재사용한다.

```bash
python main.py --mode ingest-files --path data/manuals    # 폴더 전체
python main.py --mode ingest-files --path 안내문.pdf       # 단일 파일
```

| 형식 | 방식 | 비고 |
|------|------|------|
| PDF | pdfplumber | 텍스트 레이어 기반 (스캔 이미지 PDF는 추출 불가) |
| HWPX | 표준 zip + XML | 의존성 없음, 가장 안정적 |
| HWP | olefile(PrvText) | 본문 추출, 표·서식은 누락 가능 |

- 의존 라이브러리 미설치/파싱 실패 시 **크래시 없이 해당 파일만 건너뜀**.
- 가상 URL `file://<상대경로>`로 식별 → 기존 중복제거(content_hash + chunk_id) 그대로 동작.

### 변경 파일
- [crawler/file_loader.py](../crawler/file_loader.py) — 신규 (형식별 텍스트 추출 + 적재)
- [main.py](../main.py) — `run_ingest_files()`, `--mode ingest-files` / `--path` 추가
- [config.py](../config.py) — `FILE_INGEST_DIR`, `FILE_INGEST_CATEGORY`
- [requirements.txt](../requirements.txt) — `pdfplumber`, `olefile`

## 4. 첨부파일 노출

게시물에 달린 PDF/HWP 등 다운로드 파일을 답변 출처 카드에 표시한다. 기존에는 크롤러가
링크를 BFS 탐색용으로만 쓰고 저장하지 않아, 챗봇이 HTML 페이지만 출처로 제시했다.

### 데이터 흐름 (전 구간 연동)
```
크롤러 _extract_attachments  →  raw_pages.attachments(JSONB)
   →  processed_chunks.attachments  →  documents.metadata.attachments
   →  retriever.format_context (출처 dict)  →  app.Source 모델  →  프론트 📎 링크
```

- **추출 규칙**: href가 문서 확장자(.pdf/.hwp/.hwpx/.doc/.xls 등)로 끝나거나
  정부표준 다운로드 엔드포인트(`FileDown.do`, `cmm/fms` 등)를 가리키는 `<a>`만 수집.
  `javascript:fn_egov_downFile(...)`처럼 URL 복원 불가한 스크립트 핸들러는 제외.
- **format_context 견고화**: `documents.metadata`의 attachments가 환경에 따라 list 또는
  JSON 문자열로 올 수 있어, 문자열이면 파싱 후 `{name,url}`만 통과.

### 변경 파일
- [crawler/saha_crawler.py](../crawler/saha_crawler.py) — `_extract_attachments()`, `PageData.attachments`
- [database_db/database.py](../database_db/database.py) — `save_raw_page`/`upsert_raw_page`/`save_chunks_bulk`에 attachments 저장
- [processor/data_cleaner.py](../processor/data_cleaner.py) — `CleanedChunk.attachments`, `process()` 전달
- [main.py](../main.py) — process/embed/incremental/ingest-files 메타데이터에 attachments 포함
- [chatbot/retriever.py](../chatbot/retriever.py) — `format_context()`에서 출처에 attachments 부착
- [app.py](../app.py) — `Attachment` 모델, `Source.attachments`
- [static/js/chat.js](../static/js/chat.js) — 출처 카드 아래 `📎 파일명` 링크 렌더
- [static/css/style.css](../static/css/style.css) — 첨부 링크 스타일
- [setup_supabase.sql](../setup_supabase.sql), [scripts/migration_attachments.sql](../scripts/migration_attachments.sql) — 스키마 컬럼 추가

### ⚠️ 적용 절차 (운영 DB)
1. Supabase SQL Editor에서 [scripts/migration_attachments.sql](../scripts/migration_attachments.sql) 1회 실행 (멱등)
2. `python main.py --mode incremental` 로 재크롤링 → 첨부 추출·재임베딩

> 실측: 재크롤링 후 raw_pages 19페이지 / documents 46청크에 실제 첨부 캡처 확인
> (통계연보 16개, 도로명주소 안내도 PDF, 차수판 신청서 HWP 등).

## 5. 첨부 페이지 검색 랭킹 개선

첨부 노출 기능을 붙인 뒤, "사하구 도로명주소 안내도"처럼 자연스러운 질문에서 정작 첨부가
달린 페이지가 출처로 안 잡히는 문제가 드러났다. 두 가지 원인을 수정.

| 원인 | 증상 | 수정 |
|------|------|------|
| 카테고리·서비스 **동시(AND) 필터** | "사하구 도로명주소" → category(사하소개)+service(교통) 둘 다 만족하는 청크가 거의 없어 페이지 누락 | **단일 facet만** 사용 (service 우선, 없으면 category) |
| **직원안내(staff) 크라우딩** | "사하구" 지명만으로 staff(사하구청장)가 매칭돼 콘텐츠 페이지를 밀어냄 | staff 문서는 **담당/연락처/부서/전화 등 인물·연락 의도 질문일 때만** 상위 노출 |

### 결과 (검색 경로 검증)
| 질문 | 이전 | 이후 |
|------|:---:|:---:|
| 사하구 도로명주소 안내도 | ❌ | ✅ 📎 PDF |
| 사하구 도로명주소 안내 받고싶어 | ❌ | ✅ 📎 PDF |
| 통계연보 / 사회조사 보고서 | ✅ | ✅ |
| 환경 담당 부서 / 복지 담당자 전화번호 | ✅ | ✅ (직원안내 유지, 회귀 없음) |

### 변경 파일
- [chatbot/retriever.py](../chatbot/retriever.py) — `search()` 단일 필터, `_CONTACT_INTENT` 게이팅

> 한계: 임베딩(MiniLM) 특성상 모든 표현을 100% 잡지는 못함. 핵심 케이스는 해결됐으나,
> 더 견고한 랭킹은 reranker/쿼리 재작성 등 추가 작업이 필요.
