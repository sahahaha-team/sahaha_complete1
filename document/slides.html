SLIDE 1

동시 접속 대응 설계 (정정판)

필요성

  • 주민 동시 접속 상황에서도 안정적 응답 필요

이번 단계에서 한 일

  • FastAPI(ASGI) 전환 + 워커 스레드풀로 동시 요청 비차단 처리
  • 검색·응답 파이프라인 최적화 (서버사이드 pgvector 검색, 임베딩·BM25 모델 1회 로딩)
  • Render 클라우드 배포

한계 및 향후 계획

  • 현재 무료 LLM(Groq) 일일 한도 대응으로 LLM 호출을 최소 4초 간격으로 직렬화 → 실제 동시 처리량 제한. 부하 테스트 전 운영 구성에서 제거 예정
  • 실제 대규모 동시 접속 테스트는 시간·환경 제약으로 향후 고도화 단계에서 검증 예정
  • 추후 Locust/K6 기반 부하 테스트로 동시 사용자 수·응답시간·오류율 검증 예정
※ 원본 대비 정정 — ① "FastAPI 비동기 구조" → 실제는 ASGI 전환 + 동기 호출을 워커 스레드풀로 위임(네이티브 async/await 아님) · ② "헬스체크 경로 구성" 삭제 — 코드에 /health 등 전용 헬스체크 엔드포인트 없음(라우트: /, /widget, /api/chat, /api/clear, /api/stats) · ③ 한계에 LLM 4초 직렬화 추가 — conversation.py의 글로벌 락으로 LLM 답변이 사실상 분당 ~15건으로 제한되어 "동시 접속 대응" 취지와 충돌하므로 명시.
SLIDE 2

기술적 난관과 해결책 (정정판)

1. RAG 검색 정확도 최적화

  • 문제: 행정 용어 검색 혼선
  • 해결: 하이브리드 검색 (BM25 + 벡터 유사도) 도입

2. 대규모 트래픽 처리 (서버 재설계)

  • 문제: 동시 접속 시 동기식(Sync) 응답 지연
  • 해결: FastAPI(ASGI) 전환 + 워커 스레드풀로 동시 요청 비차단 처리

3. 무결점 데이터 파이프라인 구축

  • 문제: 증분 크롤링 시 이전 데이터와 충돌 및 중복 발생
  • 해결: 콘텐츠 해시(MD5) 기반 Upsert + 조건부 GET으로 중복 없이 최신 상태 유지
