## 단계 2 — 우선 업무의 원문 확보와 HTML 구조 일치

우선 대상은 요일별 쓰레기 배출, 소방 체험/교육, 도서관 교육 예약, 보건소 시간·예방접종, 업무별 담당 부서/직통번호다. 이미 있는 기능을 새로 도입하는 방식으로 시작하지 마.

- `raw_html` 저장은 이미 구현되어 있다. 실제 DB 컬럼/대상 페이지 HTML 보유 여부와 평문 호환 경로 사용 여부를 확인해줘. 문서에서 확인한 지원과 실제 저장 상태를 구분해줘.
- 현재 검색 청크는 `processor/data_cleaner.py` → `crawler/saha_crawler.py`를 사용하며, 답변 원문은 `chatbot/official_content.py`의 병합셀 복원 등을 사용한다. 고정 HTML로 두 경로의 표 제목·행/열·rowspan/colspan·상위 사업명·조건/예외 보존을 비교해줘.
- 의미 손실이 재현되면 공통 파서/구조화 중간 표현을 최소 범위로 도입하거나 기존 파서를 재사용해 고쳐줘. 막연한 전체 재작성은 피하고, URL·원문 구간·자료 해시·필수 조건이 추적되게 해줘. 메뉴/푸터/게시판 목록은 행정 사실과 구분해줘.
- 페이지 본문과 첨부의 실제 누락을 구분해줘. 실패한 제공 질문을 해결하는 데 필요한 PDF/HWP/HWPX부터 처리하고 OCR은 필요성과 도구 지원을 확인한 경우만 적용해줘. 다운로드 링크 확보를 첨부 본문 수집 완료로 표시하지 마.
- 소방특화 어린이 체험, 공동주택 관리자 교육, 일반 주민 교육의 신청·대상·시간을 섞지 마. 도서관의 강좌 예약과 희망도서 신청을 구분해줘. 보건소 일반 운영시간을 개별 접종 가능 시간·장소로 대체하지 마.
- 예약 일반 안내와 현재 모집/실시간 잔여석을 구분해줘. 연동되지 않은 잔여석, 공식 근거에 없는 올해 일정·신청방법은 만들지 마. 홈페이지 조회 성공일을 본문 최신 갱신일로 취급하지 마.
- 원문이 없는 실패는 자료 부족, 원문은 있는데 못 찾은 실패는 검색 실패, 찾았지만 답을 망친 경우는 근거 선택/대화/출력 실패로 구분해줘.

- 업무·대상·연령·지역·신청 유형·요청 항목·확인 대기 조건을 구분해줘. 사용자가 새로 명시한 조건은 이전 값보다 우선하고 관련된 오래된 근거/선택 결과를 다시 검증해줘.
- 답을 달라지게 하는 미확정 조건만 한 번에 한 가지 물어봐줘. 이미 답한 조건은 다시 묻지 마. 이미 명확한 질문에는 불필요한 확인을 끼워 넣지 마.

- 자료에 답이 없는데 계속 조건을 묻는 반복을 막아줘. 충분한 조건을 받았으면 답하거나 정확히 무엇을 확인할 수 없는지와 관련 공식 출처를 알려줘. 확인 질문과 근거 부족을 충분한 답변으로 세지 마.
- 기존 선택지를 쓰더라도 자유 입력만으로 동일한 결과에 도달하도록 검증해줘. 사용자 지정 방향대로 버튼을 새로 늘리지 마.

## 단계 4 — 연락처 경로와 정확도를 유지하는 속도 개선

- 연락처 전용 파일 조회는 구청의 검색 타겟팅 피드백에 부합하므로 유지해줘. 연락처 질문이 일반 홈페이지 전체 검색/생성 모델로 불필요하게 넘어가는지 측정해줘.
- 공식 업무·지역·부서가 맞을 때만 직통번호를 안내해줘. 대표번호·직통·팩스를 구분하고 유사 단어만으로 다른 업무 담당자를 연결하지 마. 만료/조회 실패/담당 후보 복수를 별도로 처리해줘.
- “전화번호만 알려줘”와 “전화로만 신청할 수 있어?”를 구분하고, 절차+번호 복합 질문에서 한쪽을 누락하지 마. 기존 연락처 검사와 실제 API로 확인해줘.
- 검색용/답변용 원문 처리를 매번 반복하는지, 초기 원문 적재, 재정렬, 모델 호출, Worker 경합 중 실제 병목을 기존 request_metrics로 분해해줘.
- 캐시를 쓸 때 원문/모델 digest/대상·신청 조건/최신성 변경을 반영해줘. 유사한 질문이라는 이유로 서로 다른 연령·대상·부정 조건의 최종 답변을 공유하지 마.
- 정확도·충분 답변 범위를 유지하는 최적화만 적용해줘. 생성 모델 0회 경로와 실제 Gemma 선택 경로를 구분해 검증하고 모델 준비 표시를 상주 완료로 오해하지 마.
- 기존 30초 로컬 선택 제한·추론 잠금·복구 대기를 먼저 확인해줘. 성급한 시간 제한 축소나 동시 추론 증가로 정상 답변을 버리지 마. 초기화·cold/warm·동시 사용·Worker 동작 조건을 구분해줘.

## 검증과 완료 기준

각 의미 있는 업그레이드마다 다음 순서로 진행해줘.

1. 실패 원인·변경 범위를 기록하고 해당 문제와 이웃 업무를 보호하는 회귀를 실행한다.
2. 실제 로컬 웹 API로 원래 실패 및 동일 의미 표현/다른 조건/후속 대화를 확인한다. 모델 경로를 수정했다면 실제 Gemma 선택도 검증한다.
3. 답변을 공식 원문과 대조해 필요한 조건·예외·숫자·출처가 일치하는지 확인한다. 실패한 첫 실행도 보존한다.
4. 관련 변경만 지정 브랜치 `hellokack/fix-chat-rendering`에 커밋하고 GitHub에 푸시한다. 강제 푸시, `git add .`, 사용자 산출물·원본 민원 개인정보·비밀·로컬 모델 반입은 하지 않는다. 원격 반영을 확인한다.
5. 결과와 다음 작업을 문서 및 `document/project_context.md`에 기록한다. 커밋 전 검증 실패를 완료로 표시하지 않는다.

최종적으로 전체 회귀와 동일 버전의 제공 질문 기준 평가를 수행해줘. 이미 수정에 이용한 질문은 개발셋이며, 이후 새로 실행하는 질문도 실제 독립 검수 여부를 정확히 표시해줘. 담당자 검토가 없으면 독립 주민/구청 정답률이라고 부르지 마.

보고 항목:

- 제공 질문 수·파생 질문 수·시나리오 수·API 턴 수·고유 문자열 수·자동 검사 수를 구분한다.

- 분야별 필수 사실·조건/예외 보존·출처 일치·원문 최신성·잘못된 번호를 검수한다. 표본 내 W0도 전체 환각0%라는 뜻은 아니다.
- latency 중앙값/p95/최대와 cold/warm, 모델 유무, 시간초과/실패를 함께 보고한다. 실패를 빼거나 거절을 늘려 성능을 좋게 보이게 하지 않는다.
- 시작 기준과 최종의 코드/데이터 해시·시각·모델·Worker 상태를 남긴다. 서로 다른 모델/자료/질문 세트의 결과를 단일 알고리즘 효과로 설명하지 않는다.
- 제공 질문에서 재현된 오류가 남으면 원인·현재 영향·다음 조치를 명시한다. 공식 자료의 충돌·누락은 임의 창작으로 완료 처리하지 않는다.

작업은 중간에 추가 기능으로 확장하지 말고, 갱신/자료 → 검색 구조 → 후속 대화 → 검증된 병목 순으로 진행해줘. 진단 결과에 따라 순서는 조정할 수 있지만 이유를 남겨줘. 자료가 없으면 필요한 자료를 구체적으로 알리고 의존하지 않는 작업은 계속 진행해줘. 토큰이 부족해질 때는 마지막 검증 커밋, 실행 중 프로세스, 실패/미검증 작업, 다음 재현 절차를 기록해 재개할 수 있게 해줘.
